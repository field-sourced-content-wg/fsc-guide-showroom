== 学習目標

* App of Apps パターンを理解する

== App of Apps パターン

FSC は ArgoCD の **App of Apps パターン** を採用しています。

1つの「親」Application が複数の「子」Application を生成・管理する構成です。

[source]
----
親 Application (bootstrap)
├── 子 App: Operator インストール
│   ├── keycloak-operator
│   ├── cnpg-operator
│   └── mta-operator
├── 子 App: インフラストラクチャ CR
│   ├── Keycloak Realm
│   └── PostgreSQL Cluster
└── 子 App: アプリケーション
    ├── CoolStore
    └── DevSpaces Workspace
----

=== メリット

* 環境全体を1つの Git リポジトリで管理できる
* コンポーネントの追加・削除が `values.yaml` の `enabled: true/false` で制御可能
* ArgoCD が自動的に依存関係を解決しながらデプロイ

== Sync Waves による依存関係制御

Operator のインストールには順序があります。例えば、MTA Operator は PostgreSQL が先に起動している必要があります。

FSC では ArgoCD の **sync-wave** アノテーションを使用して、デプロイ順序を制御します。

[cols="1,2,3",options="header"]
|===
| Wave | 対象 | 説明

| Wave 0
| Namespace, ServiceAccount
| 基盤となるリソース

| Wave 1
| Operator Subscription
| OLM 経由で Operator をインストール

| Wave 2
| インフラ CR
| Operator が管理する Custom Resource（Keycloak, PostgreSQL 等）

| Wave 5
| アプリケーション
| 業務アプリケーションのデプロイ
|===

[source,yaml]
----
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "1"
----

IMPORTANT: Wave の番号が小さいものから順にデプロイされます。同じ Wave 内のリソースは並列にデプロイされます。

== ディレクトリ構成標準

FSC テンプレートリポジトリの標準的なディレクトリ構成です。

[source]
----
fsc-template/
├── Chart.yaml              # チャートのメタデータ
├── values.yaml             # 環境全体の設計図（Single Source of Truth）
├── templates/              # ArgoCD Application テンプレート
│   ├── _helpers.tpl
│   └── application.yaml    # App of Apps の子 Application 生成
└── components/             # 各コンポーネントの定義
    ├── keycloak/
    │   ├── Chart.yaml
    │   ├── values.yaml
    │   └── templates/
    ├── cnpg/
    ├── mta/
    └── devspaces/
----

=== 重要なファイル

* **`values.yaml`**: 環境全体の「設計図」。どのコンポーネントを有効にするか、各コンポーネントのパラメータを一元管理
* **`templates/`**: values.yaml の設定を読み込み、ArgoCD 用の Application マニフェストを動的に生成
* **`components/`**: 各コンポーネントがサブチャートとして独立したディレクトリに格納

== FSC 固有の機能: 動的変数の注入

FSC の最大の特徴は、RHDP がデプロイ時に **環境固有の変数を Helm チャートに自動注入** する点です。これにより、同じリポジトリが異なるクラスタで動作します。

=== 注入される主な変数

[cols="1,2",options="header"]
|===
| 変数 | 内容

| `deployer.domain`
| クラスタの Ingress ドメイン（例: `apps.cluster-abc123.example.com`）

| `deployer.apiUrl`
| クラスタの API URL

| `guid`
| 環境ごとの一意の識別子

| `user.count`
| ワークショップのユーザー数

| `bases.virt`
| OpenShift Virtualization が有効かどうか（true/false）

| `bases.rhoai`
| OpenShift AI が有効かどうか（true/false）

| `bases.aap`
| Ansible Automation Platform が有効かどうか（true/false）

| `litemaas.apiUrl` / `litemaas.apiKey` / `litemaas.model`
| LiteMaaS 有効時の AI モデル接続情報
|===

=== 使い方

Helm テンプレート内で `{{ .Values.deployer.domain }}` のように参照します。

[source,yaml]
----
# Route の定義例
spec:
  host: myapp.{{ .Values.deployer.domain }}
----

[source,yaml]
----
# ベースワークロードの有無で条件分岐
{{- if .Values.bases.rhoai }}
# OpenShift AI が有効な場合のみデプロイ
{{- end }}
----

IMPORTANT: これらの変数は RHDP が自動注入するため、values.yaml にデフォルト値（空文字）を定義しておくだけで動作します。

== まとめ

* **App of Apps パターン**: 1つの親 Application から環境全体を管理
* **Sync Waves**: アノテーションでデプロイ順序を制御し、依存関係を解決
* **標準ディレクトリ構成**: values.yaml を中心に、components/ でモジュール化
